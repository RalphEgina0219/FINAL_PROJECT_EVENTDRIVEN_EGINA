## 3. Changes to the database
**No existing table was changed.** Migration `113_create_password_reset_and_mail_outbox.js` creates two new tables (applied to `johnvivz_crm_db` and tested on a throwaway database, including rollback):

```sql
CREATE TABLE password_reset_tokens (
  id INT AUTO_INCREMENT PRIMARY KEY,
  user_id INT NOT NULL,
  purpose ENUM('reset','invite') NOT NULL DEFAULT 'reset',
  token_hash CHAR(64) NOT NULL COMMENT 'SHA-256 of the token; the raw token is never stored',
  expires_at DATETIME NOT NULL,
  used_at DATETIME NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  UNIQUE KEY password_reset_tokens_hash_uq (token_hash),
  INDEX password_reset_tokens_user_idx (user_id, used_at),
  CONSTRAINT password_reset_tokens_user_fk FOREIGN KEY (user_id) REFERENCES crm_users(id) ON DELETE CASCADE
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE mail_outbox (
  id INT AUTO_INCREMENT PRIMARY KEY,
  user_id INT NULL,
  to_email VARCHAR(254) NOT NULL,
  subject VARCHAR(200) NOT NULL,
  body_text TEXT NOT NULL,
  template VARCHAR(40) NOT NULL COMMENT 'verify_email, reset_password, staff_invite',
  transport ENUM('log','smtp') NOT NULL,
  status ENUM('logged','sent','failed') NOT NULL,
  error VARCHAR(255) NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  INDEX mail_outbox_created_idx (created_at),
  INDEX mail_outbox_to_idx (to_email, created_at),
  CONSTRAINT mail_outbox_user_fk FOREIGN KEY (user_id) REFERENCES crm_users(id) ON DELETE SET NULL
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;
```

- Email verification uses the existing `email_verification_tokens` table and the existing `crm_users.email_verified_at` and `customer_accounts.status = 'pending_verification'` columns, so they needed no change.
- Other statements the migration runs: none.
- `docs/sql/johnvivz_crm_db_schema.sql` was regenerated (59 tables, 2 triggers).
- `johnvivz_tech` was not touched: users 10, tickets 40, activity logs 20, as before.

## 4. Rules enforced by the server (Teams & CRM Access)
- **Grant:**
  - The HR status must be active or on leave.
  - The employee needs a work email and must not already have a login.
  - The Manager grants Team Leader or Agent only; the CRM Manager login stays with the setup account.
- **One active Team Leader per team.**
- **Role or team changes** are blocked while the person has active cases ("reassign them first"). Moving a Team Leader away clears their team's leader.
- **Switching access off** needs a reason. The Manager cannot change their own login or the CRM Manager login.
- **Re-enabling** never lifts an HR block: a separated employee stays blocked, and the screen says so.
- **A team** with active members cannot be deactivated.
- **HR fields** (name, email, status, position) are never written by these actions, even if extra form fields are sent.

## 6. Where the build may differ from your diagrams (please check)

The Customer Account is created with status `pending_verification`; confirming the emailed link sets it to `active` and fills `email_verified_at`. 2. **Two new tables** are not in the ERD: `password_reset_tokens` (purpose `reset` or `invite`) and `mail_outbox`. `email_verification_tokens` is now used.
3. **Grant CRM access** (use case "Manage Teams and CRM Access", actor CRM Manager):
   - It creates the `crm_users` row from an `employee_references` record with a random unusable password and sends an invitation. The staff member sets their own password.
   - The setup account keeps its emergency "create login with a temporary password" function (mock HR only).
4. **Password reset** is a new flow for all roles: request, one-time link, new password. Other sessions of that person end.
5. **Setup administrator** gains one read-only page, **Mail Log** (development mailbox). The CRM Manager cannot open it.
6. **HR reference events:** `DepartmentUpdated` and `PositionUpdated` are handled by the HR adapter (mock mode now). No CRM actor edits `department_references`, `position_references` or `employee_references`.
7. **Team rules:** one active Team Leader per team; role or team changes need zero active cases; reasons are mandatory for access changes. The Manager can neither switch off nor demote themselves.

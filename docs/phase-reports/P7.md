## 5. Differences from your diagrams, and decisions I made
1. **Request path.** ESS/HR → **P6 inbox** (signed, duplicate-safe) → `approvalService` (routing) → queue → decision → **outbox** → HR. If a diagram shows ESS writing to `approval_requests` directly, or CRM answering ESS synchronously, it differs.
2. **"Agent → Team Leader → Manager" is the escalation chain, not a skip list.** If the Team Leader is invalid the request goes to the **exception queue** (the Manager sees why and acts), not silently to the Manager. The Manager's own request and a team without a leader also go to exceptions.
3. **The exception queue has three outcomes**: assign, decide directly, **return to HR** (a decision value `returned` that the table already allowed). If your diagram has only approve / reject, add "returned to HR".
4. **Re-routing.** A pending request moves to the exception queue when its approver becomes invalid. Add this transition to the state diagram (pending → exception).
5. **Mock source and the Mock ESS page** (setup only) exist because there is no real ESS. A mock-source decision is never sent, even with HR live.
6. **Feature off keeps inbound requests as `ignored`**, reprocessable later, instead of dropping them.
7. **CRM notifies the requester** in the CRM bell when their request is decided (if they have a CRM login). ESS/HR remains the place where employees see their requests.
8. **No new tables.** `approval_requests` was enough; the diagram of tables is unchanged (one new permission).
9. **Only three request types.** The ENUM keeps `other`, but CRM refuses it.

## 6. Changes to `integration-contract.md` (send this list to your teammates)
1. New **DRAFT**: employee request approvals (§5.1). HR/ESS sends `EmployeeRequestSubmitted` (leave, attendance correction, overtime) and CRM sends `EmployeeRequestDecided` back. HR keeps ownership of every leave, attendance and overtime record.
2. `EmployeeRequestSubmitted` is a defined inbound event with required fields per request type (§5.1). With `APPROVALS_ENABLED=false` CRM stores it as `ignored`; a malformed request is `dead` with the reason.
3. `EmployeeRequestDecided` is now published, one per request: `decision` = `approved`, `rejected` or `returned`, **`reason` required for `rejected` and `returned`**, idempotency key `EmployeeRequestDecided:<request_id>`.
4. Routing rules written down: Agent → Team Leader → CRM Manager; Team Leader → CRM Manager; nobody approves their own request; no valid approver → exception queue; never auto-approved.
5. Decisions on requests from CRM's own mock source are never delivered, even when HR is live.
6. New and rewritten open questions: **5** (is the request format acceptable? does HR want `reason` on approvals? what does HR do with `returned`?), **11** (is `employee_id` the id CRM gets in `EmployeeCreated`?), **12** (is a changed request a new `request_id`?), **13** (should HR send only CRM staff's requests?).

## 7. Open points and limits
- **The request format is a draft.** If the ESS team changes field names or types, `parseRequest` in `services/approvalService.js` and the mock ESS form are the only places to change; the fake HR checks are in `tests/support/contractSchemas.mjs`.
- **Several Managers.** A Team Leader's request goes to the "Manager queue": any active Manager other than the requester can decide it. With one Manager (today) that is that person.
- **No expiry or reminders** for pending requests (and no auto-approval by design). The Manager sees the age and the exceptions; reminders can come in P8 if you want them.
- **Resubmission** (a changed request after a decision) is unanswered (question 12); a repeated `request_id` is treated as a duplicate.
- The sideways-scrolling tables on older pages (§0) are not fixed.

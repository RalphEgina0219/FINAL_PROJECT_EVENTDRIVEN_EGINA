## 1. What was done
| Area | What now works |
|---|---|
| **Signed inbound API** | `POST /api/integration/v1/events` and four read endpoints (`routes/integrationApi.js`), mounted **before** the session, flash and CSRF middleware: no cookie, no login, no CSRF token, only the HMAC. One inbound secret per app (`JVZ_CRM_INBOUND_SECRET_*`); an app with no secret set is refused. A timestamp more than 5 minutes off (either direction) is refused. **Replay protection:** every accepted signature is stored (`integration_request_nonces`); the same signed request again is `401 replayed_request`. The signature covers the method, the path **including the query string**, the timestamp and the SHA-256 of the exact body bytes. An app whose adapter is mock or disabled is answered `503 integration_not_live`. Each app may send only its own event types. |
| **Inbox with duplicate protection** | Events are stored first (`integration_inbox`), then processed. `event_id` is UNIQUE and so is `(source, idempotency_key)`: a redelivered or re-keyed event is answered `200 duplicate` and is **not processed again**. A processing failure is `failed` and retried every 5 minutes by the background job, `dead` after 5 attempts, with a manual **Reprocess**. HR payloads lose any salary, bank, government-ID or payroll field **before** they are stored. |
| **Inbound processors** | `StockReserved`, `StockIssued`, `LowStockDetected`, `ProductCreated/Updated/PriceUpdated`, `StockUpdated`, `StockUnavailable`, `EmployeeCreated/Updated/StatusChanged`, `Department*`, `Position*`. `EmployeeRequestSubmitted` is stored and ignored with a note (P7). The status and reference changes go through the **same** `applyEmployeeStatus` / `applyDepartmentUpdate` / `applyPositionUpdate` write paths P1 and P2 built, so access revocation and the audit rows are identical in mock and live. |
| **Outbox dispatcher** | `services/integration/outboxDispatcher.js`, run every 20 seconds by the scheduler and by the **Send pending events now** button. Signed `POST {target}/api/integration/v1/events`. `202`, or `200 duplicate`, = delivered. Retries after the 1st to 5th failure: **+1 min, +5 min, +15 min, +1 h, +6 h**; the **6th failure = dead letter**. A `400` from the receiver is dead at once; `401`/`403`/`5xx`/timeouts are retried. Mock and disabled events are never touched or sent. Two passes never overlap; a row is claimed before it is sent. |
| **Dead-letter queue** | Dead events show on Integration Health with their error and a **Retry** button (fresh schedule, sent at once, audited); **Retry all dead letters** needs a reason (audited). |
| **Live adapters (off by default)** | **Inventory:** products (paged list), detail, availability, price, reserve, release, health. **HR:** first load (paged departments, positions, employees), employee lookup, health. **Accounting:** health, plus event delivery by the dispatcher. Every call is signed, logged (endpoint, status, duration, mode; never a secret) and has an 8-second timeout. |
| **Checkout restructured** | Order of work: **A** check customer, address, Inventory's current price and availability, promotion and payment (nothing reserved yet); **B** **reserve** through Inventory (idempotent on the order id, `Idempotency-Key: reserve:<order_id>`); **C** save order, items, payment and `OrderConfirmed` in **one transaction**. If saving fails the reservation is **released at once**; if that release fails too, a clean-up task retries it. A lost reservation answer is repeated once (safe: idempotent); if there is still no answer the order is **not** placed and a task finds out what Inventory holds and releases it. Cancelling an order releases through Inventory after the commit (a failure is queued, the cancellation stands). |
| **Integration Health** | Real page for the CRM Manager (Settings tab) and the setup System Administrator (`/setup/integration`): each app's mode, whether the URL and the two secrets are set (never their values), last good call and last error, **Test connection**, counters, unmatched sales, outbox and inbox with filters, clean-up tasks, recent calls. Mock-only mode shows an amber note that nothing leaves CRM. |
| **Unmatched-sales reconciliation** | Report with date filters, CSV download and an "only problems" filter. Per completed sale: the `SaleCompleted` state for Inventory and Accounting, and an overall result: **confirmed**, **in progress** (under 24 h), **unmatched** (24 h or more without acceptance) or **not sent** (mock/disabled, nothing to match). Also on Integration Health, on the Manager dashboard and as a served API. "Confirmed" means the target *accepted* the event; CRM cannot see Accounting's ledger (contract question 8). |
| **Data CRM serves** | `GET /customers/{id}` (no contact data), `/orders/{id}`, `/sales/{id}`, `/reconciliation/sales`, `/health`, each limited to the apps in the contract (HR gets `403` on all data endpoints). |
| **Event data = contract** | The four events published since P5 did not match `integration-contract.md` v0.2 field for field. I changed the code to the contract (money as decimal strings, `items`, `totals`, `release_items`, `approved_by_employee_id`, ISO times with `+08:00`), and the fake servers reject any drift. See §6. |
| **Contract v0.3** | `docs/integration-contract.md` rewritten; the change list for your teammates is §10 of that file (also copied in §7 below). |

## 2. Database changes (migration 117, show-SQL rule)
**No existing table was altered.** Two tables were created and one permission was added (`migrations/117_p6_integration.js`; applied to the test databases by the suites):
```sql
CREATE TABLE integration_request_nonces (
  signature CHAR(64) NOT NULL PRIMARY KEY COMMENT 'hex HMAC of an accepted request',
  client VARCHAR(40) NOT NULL,
  received_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
  INDEX integration_nonces_received_idx (received_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

CREATE TABLE integration_compensations (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  kind ENUM('release_reservation','resolve_reservation') NOT NULL,
  `system` VARCHAR(40) NOT NULL DEFAULT 'johnvivz_inventory',
  order_id CHAR(36) NOT NULL,
  reservation_ref VARCHAR(64) NULL,
  correlation_id CHAR(36) NULL,
  lines_json JSON NULL COMMENT 'order lines, kept for resolve_reservation',
  reason VARCHAR(200) NULL,
  status ENUM('pending','done','dead') NOT NULL DEFAULT 'pending',
  attempts INT NOT NULL DEFAULT 0,
  next_attempt_at DATETIME NULL,
  last_error VARCHAR(500) NULL,
  is_mock TINYINT(1) NOT NULL DEFAULT 0,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  done_at DATETIME NULL,
  UNIQUE KEY integration_compensations_uq (kind, order_id),
  INDEX integration_compensations_due_idx (status, next_attempt_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

INSERT INTO permissions (code, module, description) VALUES
 ('integration.manage','settings','Integration Health actions: send pending events, retry dead letters, test a connection');
-- role_permissions: integration.manage -> crm_manager, system_admin   (integration.view already existed since migration 102)
```
`down()` removes the permission and both tables (the P1 rollback check proves it). The tables `integration_outbox`, `integration_inbox` and `integration_logs` already existed from migration 110 and were **not changed**: their status values were enough. `johnvivz_tech` was not touched. The mock Inventory still keeps its data only in `crm_settings` (test overrides `mock_inventory.*`, and now short-lived `mock_reservation.*` rows, see §6).

## 5. How to switch a live adapter on (not done; do it only after the team confirms)
In `.env`: set `INTEGRATION_<APP>_MODE=live`, `<APP>_API_BASE_URL`, `JVZ_SECRET_<APP>` (what CRM signs with) and `JVZ_CRM_INBOUND_SECRET_<APP>` (what that app signs with when it calls CRM), restart, then press **Test connection** on Integration Health. Exchange the two secrets with the team on a private channel. The demo seed is mock data; do not seed into a live database.

## 6. Differences from your diagrams, and decisions I made
1. **Checkout sequence.** If your diagram shows "reserve stock" inside the create-order step, it is now **reserve first, then save, then compensate** (§1). Add the compensation arrows (release on failure; resolve and release when no answer arrives).
2. **Two new tables** (`integration_request_nonces`, `integration_compensations`): add them to the database diagram (61 tables).
3. **Mock reservations.** Because the reservation now happens before the order exists, the mock Inventory keeps a short-lived `crm_settings` row `mock_reservation.<order_id>` (30-minute lifetime, removed when the order is saved or released). Mock only.
4. **No "issue stock" call.** In live mode Inventory consumes the reservation when it receives `SaleCompleted`. A completed order shows stock **Reserved** until Inventory sends `StockIssued`; in mock mode it is Issued at once. If your sequence diagram has a separate issue call, replace it with the event.
5. **Event data changed to the contract** (money as strings, `items`/`totals`, no VAT fields, ISO time with `+08:00`). Any diagram that lists the P5 field names (`lines`, `net_amount`, `reservation_ref`, `vat_computed_by`) is out of date.
6. **Retry wording.** v0.2 said "dead after the 5th failure" but listed five retries. It is 6 attempts, dead after the 6th failure (the contract is fixed).
7. **"Confirmed" in reconciliation means accepted by the target**, not "posted in the ledger" (no posting feedback exists yet; contract question 8).
8. **Each Integration Health URL belongs to one role**: the Manager opens `/crm/settings/integration`, the setup administrator `/setup/integration`; each gets 403 on the other's URL.
9. **Inbound events from an app in mock or disabled mode are refused (503)** so mock mode can never absorb real data.

## 7. Changes to `integration-contract.md` (send this list to your teammates)
1. Signature `path` **includes the query string**.
2. **Replay protection**: a signature is accepted once; senders re-sign every attempt.
3. Error codes defined: `401` (`unauthorized`, `invalid_signature`, `stale_timestamp`, `replayed_request`), `400`, `403`, `503 integration_not_live`.
4. Retry rule fixed: 6 attempts, dead after the 6th failure; `400` dead at once.
5. Event `data` follows the §4 tables exactly (money decimal strings, ISO times with `+08:00`, `items`, `discounts`, `totals`, `payments[reference_no, paid_at]`, `release_items`, `approved_by_employee_id`; no VAT split).
6. `SaleCompleted` makes Inventory consume the reservation; `StockIssued` is the optional answer.
7. Which app may send which event (anything else `400`); expected `data` of every inbound event.
8. Response shapes for the Inventory and HR calls, paging, `409` on a refused reservation, `404` on release = already released.
9. Reservation is **idempotent on `order_id`** with an `Idempotency-Key`; CRM reserves before saving and releases on failure.
10. Proposed endpoints: `GET /health` on every app; HR `GET /departments`, `/positions`, `/employees` (paged).
11. Served APIs and reconciliation defined in detail (§7, §8).
12. New open questions: reservation expiry (1), Accounting posting event (8), Inventory `StockReserved`/`StockIssued` (9), health endpoint (10).

## 8. Open points and limits
- **The contract is unconfirmed.** Anything the teams change means a code change here; the adapters are small and the fakes in `tests/support` are the place to update first.
- **Reservation expiry** is a safety net CRM asks Inventory for (question 1); CRM does not depend on it.
- **Single server.** The replay guard and the dispatcher claim use the database, so two CRM processes are safe; the rate limiter on the inbound API is in memory (per process).
- **HR first load** needs the paged list endpoints, which are proposals (question 7). Without them HR data arrives only through events and lookups.
- The inbound API does not yet give Accounting a posting-confirmation path (question 8).
- `integration_logs` has no retention rule yet (P10).

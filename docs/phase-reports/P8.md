## 2. Database changes
**One approved change to an existing table**, plus one new table and two permission rows (applied to `johnvivz_crm_db`, batch 8):
```sql
-- 119 (approved by you on 2026-11-14)
ALTER TABLE approval_requests
  MODIFY status ENUM('pending','approved','rejected','returned','exception','superseded') NOT NULL DEFAULT 'pending';
INSERT INTO permissions (code, module, description) VALUES ('requests.view_own','approvals','See the status and result of my own employee requests (read-only; filed and owned in ESS/HR)');
-- role_permissions: requests.view_own -> agent, team_leader, crm_manager

-- 120 (new table only)
CREATE TABLE loyalty_redemptions (
  id INT AUTO_INCREMENT PRIMARY KEY,
  loyalty_account_id INT NOT NULL,
  sales_order_id INT NOT NULL UNIQUE,          -- one redemption per order
  redeem_transaction_id INT NOT NULL,
  points INT NOT NULL,
  amount DECIMAL(12,2) NOT NULL,               -- points / 100 * 10
  status ENUM('applied','returned') NOT NULL DEFAULT 'applied',
  return_transaction_id INT NULL,
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  CHECK (points > 0 AND MOD(points, 100) = 0 AND amount > 0),
  FOREIGN KEY (loyalty_account_id) REFERENCES loyalty_accounts(id),
  FOREIGN KEY (sales_order_id) REFERENCES sales_orders(id),
  FOREIGN KEY (redeem_transaction_id) REFERENCES loyalty_transactions(id),
  FOREIGN KEY (return_transaction_id) REFERENCES loyalty_transactions(id)
);
INSERT INTO permissions (code, module, description) VALUES ('loyalty.view','sales','View loyalty accounts and their earn / redeem / reversal history');
-- role_permissions: loyalty.view -> crm_manager
```
Why a new table: `loyalty_transactions` has no link to the order that used the points. Without one, a cancelled order could not give its points back exactly once. `loyalty_accounts` and `loyalty_transactions` (migration 107) were used as they are. A reversal is stored with `refund_id` and no `sales_transaction_id`, so the existing unique key (one earn per sale) still holds when one sale has several refunds. `johnvivz_tech` was not touched.

## 5. Differences from your diagrams
1. **Loyalty has no tiers.** The schema's `loyalty_accounts.tier` stays empty (decision D13 has no tiers); any Gold/Silver/Bronze in a diagram is not built.
2. **New table `loyalty_redemptions`** (order ↔ points used). Add it to the ER diagram, linked to `loyalty_accounts`, `sales_orders` and `loyalty_transactions`.
3. **Points flow:** completed sale → earn; recorded refund → reverse; checkout → redeem; cancelled order → return ("adjust" type). If a diagram shows points awarded at payment or at order time, it differs: points are earned only when the sale is completed.
4. **Approval request states:** add **Superseded** (pending or exception → superseded when a changed request arrives). It is not a decision.
5. **My Requests** is a new read-only view for staff. It is not in supplement E's menus (as you asked), and is reached from My Account and the dashboards.
6. **Team targets** are SLA-compliance figures from `service_targets`, not sales targets.

## 6. Open points
- **A refund after the points were spent:** CRM takes back only what is still in the account (the balance cannot go below zero) and writes the shortfall in the reason. If you want a different rule (for example, reduce the refund by the points' value), it is a business decision, probably for Accounting.
- **Demo data and points:** demo sales earn demo points like real ones (they are removed by `seed:clear`). No demo order redeems points: 100 points need ₱10,000 of purchases, which the demo sales do not reach.
- **Several redemptions per order** are not allowed (one per order, by design).
